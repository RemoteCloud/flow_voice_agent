# flow_voice_agent — working notes for Claude Code

Three deliverables in one repo, same concept as `streamdeck_maranics_flow` (one hub process,
Maranics UserManagement OIDC sign-in, device tokens, web UI; every device is a thin client):

- **Hub** `server/` (Node 20, TypeScript, Hono + ws, esbuild → `dist/server.mjs`). Entry `server/main.ts`.
- **PWA** `web/` (React 19 + Vite 6 + Tailwind 4 + vite-plugin-pwa → `dist/public/`, served by the hub on the same origin).
- **Android agent** `android/` (Kotlin, AGP 8.5.2, minSdk 26 / target 34): a WebView hosting the PWA plus
  on-device TTS/STT and a `microphone` foreground service. `MainActivity.Bridge` ↔ `web/src/audio.ts`.

The architecture spec the code follows is `docs/SPEC.md` (Flow Voice v0.2). Section numbers in code comments refer to it.

## Architecture (server/)

- `protocol.ts` — shared contract: control types, `RunView`/`RunItem`, AEP frames (`EndpointMessage` / `HubToEndpointMessage`), events, WS close codes. Imported by the web app too — change it with both sides.
- `env.ts` — pure env parsing (`HUB_*` names kept for parity with FlowDeck; `FLOW_API_URL`, `STT_ENDPOINT`, `DEV_USER`, `SERVICE_TOKENS`, `WEBHOOK_SECRET(S)` …). Smoke-tested.
- `store/HubStore.ts` — one JSON document (`/data/hub.json`, atomic write). Portable files on the volume (`stations.json`, `mappings.json`, `profiles/*.json`: author once, copy to the next vessel) are imported on a fresh hub and again only when the file changed (`portableSeen` mtimes in hub.json); otherwise what Admin saved stands, so a restart never rolls stations back. `store/credentials.ts` unseals + refreshes **per-session** Maranics tokens: every write is attributed to the user who answered — there is no service account for writes.
- `maranics/FlowsClient.ts` — Checklist API v3 (`{host}/app/flows/v3` on the gateway, `/api/v3` on the service) + Templates API. Routes verified against `ChecklistApp/Maranics.Checklist.IntegrationTests/V3WriteApiTests.cs`: `PUT /flows/{id}/tasks/values {items:[{task, value, overrideExistingValue}]}`, `POST /flows {templateId}`, `PATCH …/tasks/{ref}/state`, `POST /flows/{id}/status {action}`. `task` accepts a task id **or a DataId**.
- `voice/interpret.ts` — deterministic parsers per `Control.Type` (time expressions anchored on `utteredAt`, clock digits, numbers in words, yes/no lexicon, fuzzy but bounded QuickSelect), control vocabulary, `stripPhrase` (bound phrase or a tail of the item name). Thresholds per type; below → clarify, never guess.
- `voice/i18n.ts` — every spoken string in en/sv/no/fr/de (`t(lang, key, params)`), `spokenNumber(n, lang)`, `normLang`, `localeTag`. Add a key to all five tables. The interpreter understands all five languages at once; `i18n.smoke.ts` covers each.
- `voice/checklist.ts` — flow → spoken items (section order, task order), readiness (`full` / `partial` / `none`), announcements.
- `voice/RunEngine.ts` — the dialogue state machine per run: `speakItem → openListen → onTranscript → readback → commit → advance`, timers (listen / confirm / exchange), retries, escalation, skip sweep, pending (triggered) runs, single-item prompts as one-item runs (`prun_<promptId>`), pause/resume/complete/discard/abandon, restart recovery. All device I/O goes through `EngineIo` (implemented by `ws/Gateway.ts`).
- `voice/Outbox.ts` — durable queue in the store, backoff, ordered per instance, `VALUE_OVERWRITE_CONFLICT` → one retry with override. `drain()` joins an in-flight pass (so `commit()` learns the real outcome).
- `ws/Gateway.ts` — `/v1/audio` (AEP: one active endpoint per station, observers, takeover, PCM buffering only inside a listen window, HTTP STT adapter) and `/v1/events`.
- `http/app.ts` — `/api/*` (cookie session), `/v1/*` (service token or `X-Flow-Signature` HMAC, `Idempotency-Key` replay before validation), ops endpoints, static PWA with SPA fallback. `http/auth.ts` is the OIDC broker (ported from FlowDeck, per-session credentials, plus `DEV_USER` sign-in). `http/session.ts`, `rateLimit.ts`, `static.ts`, `oidc/*`, `store/crypto.ts`, `core/*` are copied from the FlowDeck hub.
- `speech/stt.ts` — `EndpointStt` (device transcribes, default) / `HttpStt` (OpenAI-compatible `/v1/audio/transcriptions`, WAV upload, bias words as `prompt`).

## Light multi-tenancy (`server/tenants.ts`, `main.ts`)

For trying other Maranics tenants, not a full tenant model. `main.ts` `buildCore(env)` builds one isolated hub (store, credentials, auth, outbox, engine, gateway, app); the main hub is the env-configured core, and every entry of `HubData.tenants` (main hub only: name, Maranics tenant id, optional host, pasted access token sealed with the hub key) is a second core with `dataDir = <data>/tenants/<id>`, no OIDC, and the dev sign-in path (`devUser` + `devToken` = the pasted token, `env.tokenTenant` set). So stations, register, words, runs, sessions and audit are separate per tenant, and every Flow write is attributed to the token's owner.

- **Normal tenant = Maranics SSO with its own client**: `TenantEntry.clientId` + `clientSecretEnc` (sealed) + optional `issuer` (default: the main hub's issuer with the tenant segment swapped, `issuerFor`). Its core gets a real `oidc` env (redirect = `{HUB_PUBLIC_URL}/api/auth/callback`, the same for every tenant: the `fv_tenant` cookie, SameSite=Lax, routes the callback), no dev user; people sign in as themselves and the first one becomes that tenant's admin. `GET /t/<id>` (SSO tenants only) sets the cookie and redirects to `/admin` (`?to=client` → `/client`). `PUT /api/tenants/:id/client {clientId, clientSecret}` replaces the client. The pasted-token mode below is the fallback when no client exists yet. The add form has a visible **Maranics server address** (`TenantEntry.host`, within `HUB_ALLOWED_HOSTS`, empty = the main hub's, which `GET /api/tenants` reports as `mainHost`); for another server the issuer is found by `resolveIssuer` at add time: the typed one (tenant segment appended when missing, `withTenant`), else the first of `usermanagement.<env>/<tenant>` and `administration.<env>/<tenant>` (edge servers) that answers OIDC discovery (`issuerCandidates`); the UM API is `<issuer origin>/external/api`.
- **Tenant + location**: `TenantEntry.location` (add form field "Location", `POST /api/tenants {name, location, …}`) lets the same tenant name and Maranics tenant id be added once per vessel / site, each with its own server address, client id + secret, data and `/t/<name>-<location>` link; shown as "Color Line / Color Magic". After adding one with a location the form keeps name, tenant id and sign-in address for the next.
- **Several servers per tenant** ("colorline / colormagic", one per vessel): `POST /api/tenants/:id/servers {name, host, issuer?}` (`addServer`) copies the tenant's Maranics tenant id and client (or token) into a new entry `<root>-<slug>` with `parent` set, its own host, data folder, stations and `/t/<id>` link. Issuer given = people sign in at the same place; empty = worked out from the server address. Optional `clientId` + `clientSecret` (both or neither) give the location its own client instead of the shared one. Central lists locations indented under their tenant ("Add location").
- The dispatcher in `main.ts` picks the core per request and per WebSocket upgrade from the signed `fv_tenant` cookie (`<id>.<admin|client>.<hmac>`); an invalid / unknown cookie means the main hub. `/api/tenants*` is always answered by the main hub's `Tenants.app()`.
- Getting in: a main-hub admin (`POST /api/tenants/:id/enter` → role `admin`), or a station link of that tenant (`POST /api/auth/join` is looked up in every core → role `client`, never admin). The role reaches the core as `x-fv-tenant-role`, which the dispatcher always strips from inbound requests. `provider.auto` makes the login page sign in by itself.
- A token core's session cookie is renamed `fd_session_<id>` on the way out and back, so entering a tenant never signs the admin out of the main hub.
- Admin → Tenants: add (name, tenant id, token, optional host within `HUB_ALLOWED_HOSTS`), Open, New token, Remove (data folder stays). The token is never returned; `tokenExpiresAt` comes from an unverified peek at the JWT. `/v1/*` service calls always go to the main hub. `npm run mock` covers all of it (step "tenants").

## Conventions

- **Never log tokens.** `core/log.ts` redacts registered secrets and `Bearer …`; register new secrets with `registerSecret()`.
- **Pure modules are smoke-tested** without a framework: `server/**/*.smoke.ts` export `run()`; `npm run smoke` bundles them with esbuild and runs them. Keep `interpret`, `checklist`, `env` free of I/O.
- **`npm run mock` must stay green.** It boots the fake Maranics + the real hub + a scripted AEP endpoint and replays spec Appendix B (relative time → absolute read-back, "no" reopens, N/A bounded to options, clarification, skip sweep, completion blocked by open items, prompt with idempotent replay, triggered pending run started by voice). Extend it when the dialogue changes.
- **Fake Maranics** `scripts/lib/fake-maranics.mjs` is the FlowDeck fake extended with controls/values/create/status. Fixtures: `tpl-engine`, `tpl-departure`, `NauticAI/ArrivalChecklist` (+ flow `flow-arr-1`). Static token `t0k3n`, tenant `demo`.
- **No-hands operation**: `RunEngine.onMenuTranscript` / `speakMenu` (list · name/number · station …) run when no run is active; `beginComplete` / `beginDiscard` / `onActionAnswer` are the two-step voice confirmations (`RunRecord.pendingAction`, gated by `Station.voiceActions`, default on). The hub moves screens with `navigate` frames (`EngineIo.navigate`), handled by `web/src/voice.tsx` (`VoiceProvider`, the app-wide voice session; `VoiceBar`). `npm run mock` covers menu, discard-cancel, complete-by-voice and station switch.
- **Hands-free** lives entirely in `web/src/audio.ts`: an idle listen window (`promptId === "idle"`) re-arms between prompts, is closed while TTS plays, and echo-guarded against the hub's own voice; the hub just receives ordinary `transcript` frames (idle → commands / unprompted phrase answers in `RunEngine.onTranscript`). Android and `audioPolicy: "open"` stations auto-start voice (`Run.tsx`).
- **Speech runs on the endpoint by default.** Audio buffers live only between `listen.open` and `listen.close`; the audit record is text. The one exception is the opt-in training recorder below — add no other audio persistence.
- **Recording answers for training** (`server/speech/capture.ts`, Admin → Stations → "Record answers for training", `Station.recordVoice`, off by default): the hub sets `listen.open.record`, the browser streams PCM next to its own recogniser for that window (`startTap` in `audio.ts`; the Android agent does not record yet), and `Gateway.answer` hands the window to `VoiceRecorder` with `RunEngine.captureContext` (before) / `captureOutcome` (after). A clip = 16 kHz WAV + JSON sidecar (`flow-voice.capture/1`: flow, item with answer/trigger words, prompt, transcript + alternatives, what it changed; speaker = HMAC pseudonym, no name). Queued in `<data>/captures/`, uploaded to S3-compatible storage (`CAPTURE_S3_*`, SigV4 in-house, no SDK, smoke-tested against the AWS vector) as `<prefix>/<core>/<template>/<date>/<clipId>.wav|.json`, back-off when offline; without a bucket kept locally under `CAPTURE_MAX_MB`. `GET /api/captures` / `POST /api/captures/flush` (admin). The run screen says "Answers are recorded for training" (`RunView.recording`). Central switch: `HubData.recording {enabled, off[]}` in the main hub's hub.json (`/central` card "Recording answers for training", `GET`/`PUT /api/central/recording {enabled} | {core, allowed}`, `RecordingSwitch` in `CentralRecording.tsx`, shown at the top of the tenants screen); off by default, and a station records only when it is on hub-wide, its core ("main" or tenant entry id) is not in `off`, and the station ticks `recordVoice` (`recordingAllowed(coreId)` in `main.ts`, read live). `npm run mock` step "voice recording".
- **Mobile client = run + voice only.** `web/src/platform.ts` `isMobileClient()` is true inside the Android WebView (`window.FlowVoiceAndroid`) and on any phone browser / installed PWA (user agent); `?mobile=1` / `?mobile=0` force either layout and are remembered. Mobile gets a one-line header ("location · station" pill, theme toggle, no Admin tab), `web/src/pages/Home.tsx` (one big Continue button for the open run on this station + 2-column icon tiles from `web/src/icons.tsx` `iconFor(templateName)`), and a run screen with an "Up next" strip and an always-visible done / now / next item list but no typed input / hands-free switch / event log; `#/admin` falls back to Home. `Home.tsx` (big start buttons) is the client view in the desktop browser too (`mobile={false}`: station picked on screen); Admin stays browser-only.
- **Station QR join** (Admin → Stations → per-station card): `POST /api/stations/:id/join-token` (admin) mints a `fvj_` token shown once; only `sha256` + hint live in `HubData.stationJoins` (hub.json, deliberately *not* the portable `stations.json`); `DELETE` revokes. **Station code** (Netflix-style pairing): every join also carries a six-digit `StationJoin.code` (`newJoinCode`, unique across the main hub and every tenant core via `AppDeps.joinCodesElsewhere` / `Tenants.joinCodesExcept`; `ensureJoins` gives old joins a code without rotating the link). `POST /api/auth/join {code}` (`normalizeJoinCode` in `protocol.ts`, spaces allowed) does exactly what the token does, under its own tighter limiter (`JOIN_CODE_LIMITS`, 8 per IP / 60 hub-wide per 15 min); the dispatcher finds the tenant with `coreOfJoinCode`. Admins see it on the card and the printed poster (`StationView.join.code`, `JoinTokenResponse.code`); "New link" rotates both. Crew type it on the Home scan screen ("Or type the station code", `StationCodeForm`; "Change station" on a PC opens it), in the Android menu "Enter station code…" (`askStationCode` → loads `/client#/join/<code>`, so `App.tsx` treats a six-digit `#/join/` as a code via `joinBody`) or via the bridge `enterStationCode()`. `npm run mock` step "join" covers code join, wrong / short code, rotation and uniqueness. The poster URL is `{base}/?mobile=1#/join/<token>` — the token rides in the fragment so no access log sees it. `App.tsx` scrubs the URL, `POST /api/auth/join` sets the signed `fv_join` cookie (15 min, `/api/auth`) which the OIDC callback / dev login consume into `HubSession.stationId` + `stationSource: "join"` (Home then hides the station chips; picking on screen sets `"pick"`). Encoder `server/core/qr.ts` is pure (versions 1–10, L/M/Q/H, mask selection), smoke-tested, and imported by the web app like `protocol.ts`. `Station.location` is free text shown before the name. `npm run mock` covers mint → join → dev login → bound session, invalid/revoked tokens, and audit.
- **Screen conventions** (`web/src/components/ui.tsx`): `Alert` for every inline error / note, `SaveMark` ("Saving… / Saved ✓") on screens that save at once, `RUN_STATE_TEXT` / `EXCHANGE_TEXT` / `joinNames` / `plural` for plain-language labels; never show a raw state string. The admin tab lives in the address (`#/admin/<tab>`, `AdminPage({tab})`), so refresh / back / pasted links keep the tab. On `/client` the run screen keeps the mic in a bar fixed to the bottom (`VoiceControls`, `mobile`): hold-to-talk + Repeat / Skip, or Confirm / No while a read-back waits, or Next item while held; "Stop run" asks first; the Complete button says why it is blocked. A `#/join/<token>` opened while the app already runs reloads the page so the token counts.
- **Look**: Maranics brand (Brand Guidelines v1.0, 2026; `anthropic-skills:maranics-brand`): light ground `#F6F7F8`, navy `#06182D` as text / primary button, `#007D8F` the only cyan read as text, `#00BBD6` graphics only (`--c-data`); dark theme = navy ground, white type. Tokens in `web/src/index.css`; fonts Archivo (words) + IBM Plex Mono (numbers, ECAM list) bundled from `@fontsource` so they work offline. Brandmark files in `web/public/` (`logo.svg` / `logo-on-dark.svg` lockup, `mark*.svg` symbol, `icon.svg` app icon = navy square, white gear, cyan pixels), extracted from `~/Downloads/brand-manual-maranics.pdf`; `components/Logo.tsx` swaps the file per theme. Never mirror / recolour the mark; the pixels are cyan, the gear never is. Android launcher = same symbol (`ic_launcher_foreground.xml`). The run item list is laid out like an ECAM page (`.ecam*` classes, `ItemList` in `Run.tsx`): mono capitals, `ITEM . . . . VALUE`, cyan = to do, green = done, amber = skipped / unsynced / needs screen, boxed = now; first on a phone, right column from `md` up. Home shows one big `.start-btn` per checklist.
- **Admin is save-button free**: Stations (`AdminStations.tsx`) saves selects / tick boxes at once (`pick`) and text fields on blur (`commit`), with a "Saved ✓" marker; a card shows name, vessel, menu language, noisy-place switch, a tick list of the registered checklists (ticked = only those; per ticked one "can be started here" / "only continue") and the link panel (Open on this computer · Copy · Print; new link under "Link lost…"). Technical fields and Remove sit under "Advanced settings"; JSON editing is a link at the bottom. The Status tab opens with a three-step setup guide (`SetupGuide`). Keep wording plain: no "endpoint", "rotate", "policy" in labels.
- **Central checklist register** (Admin → Checklist setup, `web/src/pages/AdminChecklists.tsx`): `HubData.library[templateId]` = template downloaded from the Templates app with a snapshot of its items (`GET /api/library`, `GET /api/library/available`, `POST /api/library {templateId}` = download / download again, `DELETE /api/library?templateId=`, `PUT /api/library/entry {templateId, language, words}`; ids travel in body / query because they may contain "/"). Language and answer words are set only here (stored in `settings.templateLanguages` / `settings.itemAnswers`): the admin taps words of the item name (or adds another word) and each change saves at once. A non-empty register is the whole offer (`templateAccess`: not registered → `off`, also for open instances); stations pick from it (start and use / use only). The old Start buttons and Answers tabs are gone; `settings.startable` only matters while the register is empty.
- **Answers per item** (Admin → Answers): `settings.itemAnswers[templateId][answerKey] = words`, key = `d:<DataId>` or `n:<lowercased name>` (`answerKey` in `checklist.ts`; items listed by `GET /api/template-items?templateId=`). `buildItems` puts them on `RunItem.expected`; `interpret` (`heardAnswer`, `ctx.answers`) accepts any transcript that contains one as whole words, never inside a negation: checkbox → checked, yes/no radio → Yes, DateAndTime → now, options → the option with that word, text → the word. The word is the read-back / ECAM value (todo rows show it: `RAMP . . . UP`), and it is added to the STT bias list and the on-device grammar.
- **Words that must come together** (Admin → Answers / Checklist setup, the button on the item: "any one word" ↔ "all words together"): one answer word written `"a + b"` is a combination — every part must be heard, in any order and any distance apart ("körbro er hivt", "hivt körbro"), each part with the usual compound / near-miss tolerance, and a negation still refuses it. `answerParts` / `answerLabel` in `interpret.ts`; stored in the same `settings.itemAnswers` list (the hub normalises `a+b` to `a + b`), read back and shown on the ECAM row without the "+", and split into its parts for the STT bias list and the on-device grammar. `containsAllWords` does the same for a phrase: `RunEngine.unpromptedAnswer` now finds the item by the name spoken as written, else by every word of the name somewhere in the sentence, else by a combination answer word (one plain word never names an item). `npm run mock` step "words together".
- **Say a word to set an item** (Admin → Checklist setup, second row on every item, "Say to set"): `settings.itemTriggers[templateId][answerKey] = { words, need }` (`PUT /api/library/entry {triggers}`, `LibraryView.triggers`, on the item as `RunItem.triggers`). Trigger words are picked exactly like answer words (tap a word of the item name or type another one) and say *which item* is meant, not what the value is; `need` is set on the item ("any one word" / "at least N" / "all N words"), order never matters and each word may itself be a combination ("hivt + körbro"). `heardTrigger` / `triggerNeed` in `interpret.ts` are pure and smoke-tested; a negation never triggers. Hearing enough of them is also the answer (`InterpretContext.triggers` → the same `byWord` branch as an answer word): checkbox → checked, yes/no → Yes, DateAndTime → now, text → the words; an options item still needs its option word, so the hub asks it. The item's own answer word always decides the value when both are said. `RunEngine.triggerHit` picks the open item with the most words heard, `takeOver` moves there and answers it (one hand-over per utterance, no ping-pong). Trigger words ride on the STT bias list and the on-device grammar. `npm run mock` step "trigger words".
- **How the crew answers** (Admin → Stations, on the card): `Station.voiceMode` `prompt` (default, today's flow: the hub reads an item and waits) / `trigger` (the hub stays quiet, the mic stays open with every open item's words on the bias list, and each utterance sets the item it names — `RunEngine.openTriggerListen`, no current item, silence just re-arms, what is left over is asked by the skip sweep at the end) / `both` (the hub reads item by item **and** a trigger word answers any other item, even while something else was asked). `RunEngine.voiceMode(r)` reads it live, so a change applies to an open run; single-item prompt runs always ask. `Station.voiceModeCrew` lets the crew step through the three from the run screen (`PUT /api/stations/:id/voice-mode`, admin always, the crew only on their own station and only when it is ticked); `RunView.voiceMode` / `voiceModeCrew` carry it to the screen.
- **Hardware buttons** (Admin → Stations, "Buttons" on the card): `Station.buttons` = up to three `{ key, action }` (`StationButton`, `stationButtons` sanitiser and `BUTTON_ACTIONS` in `protocol.ts`, smoke-tested; portable in `stations.json`). A button is a Bluetooth (HID) or USB button that the device sees as a keyboard key, paired in the OS; `key` is the DOM `KeyboardEvent.code` name ("Enter", "PageDown", "AudioVolumeUp"), learned in Admin by pressing the button or picked from a list, and one key does one thing. `web/src/buttons.ts` `useStationButtons` (mounted in `VoiceProvider`) listens in the capture phase everywhere except Admin and text fields; the Android agent catches bound keys in `MainActivity.dispatchKeyEvent` (the page hands them over with `setButtonKeys`, key codes are mapped to the same DOM names by `buttonKeyName`, the on-screen keyboard is left alone) and reports `window.flowVoiceButton(key, down)`, so a bound volume key stops being push-to-talk. The device only does `talk` (hold = push-to-talk) itself; every other press is `POST /api/runs/:id/button {action}` → `RunEngine.button`: `accept` (confirm a read-back / start a pending run / resume / release a held item / confirm complete, never discard; on an open item its answer word, else checked / Yes / now, without read-back and also on a "marked words only" checklist; a number or free text gets the hint and stays open), `no` (the item gets No and the run moves on: yes/no → No, an option named No; a checkbox / number / text is skipped with reason `no by button` and asked again at the end; a waiting read-back is asked again instead), `override` (skip, also a held item), `next`, `back` (the previous item is asked again, also after the last one; marked `reasking` so live sync keeps the old Flow value off it), `repeat`, `pause` (pause / resume). Presses are audited as `button`; the client drops a second press of the same action while the first is on its way (400 ms). Browsers never see volume keys, so a button that sends one only works on Android. `npm run mock` step "buttons".
- **Press / two quick presses / hold** (one button, up to three actions): `StationButton.double` and `.hold` next to `action` (= one press), picked on the button's row in `ButtonRules` ("Two quick presses: …", "Hold 2 seconds: …"); never `talk`, and a `talk` button has neither (`stationButtons` drops them). `buttonPresses` in `protocol.ts` (pure, fake-clock smoke test) reads the presses in `useStationButtons`: a button with only `action` fires on the way down as before; with `double` a single press waits `BUTTON_DOUBLE_MS` (500) for a second one; with `hold` the press fires on release and `BUTTON_HOLD_MS` (2000) held fires `hold` while still down. A click-only Bluetooth button (release sent only just before its next press, < 30 ms) is detected and from then on every press is a whole click (no hold; its first press may read as a hold once); a button that has once been let go on its own (no press within 30 ms) is never taken for one, and such a release ends the click-only reading — Bluetooth batches notifications, so a real PTT-Z release can land 1 ms before a quick second press (seen on the SM-T500). Nothing changes on the hub or the Android agent: they still see one action per `POST /api/runs/:id/button`. `npm run mock` step "buttons".
- **Buttons are also set on the device** (Home → "Buttons", every client incl. phones / tablets: the one settings screen they have, because the buttons are connected to that device): `ButtonSetup` wraps the same `ButtonRules` as Admin (`web/src/components/ButtonRules.tsx`: connect, "Add a button", press it, pick the action) and saves at once with `PUT /api/stations/:id/buttons {buttons}`; it lists only the buttons added to this device (`ButtonRules device`: a `Ble…` row shows only when its slot has a button paired here — `useBleButton` slot `name` / `connected`; keyboard keys and rows without a key always show), with "Show all" for the rest (admins, or any session bound to that station; audit `station.buttons`), via `AppApi.saveButtons`, which also updates the stations in the app context so the new buttons work without a reload. While a button is being learned `setButtonLearning(true)` (`buttons.ts`) stops actions from running and tells the Android agent `setButtonKeys("*")` = hand every hardware key to the page; `ble.ts` owns `window.flowVoiceButton` and passes Bluetooth and Android key presses to `onBleKey` listeners. `npm run mock` step "buttons".
- **Bluetooth push-to-talk buttons (Zello-type, not keyboards)** use the same `Station.buttons`, under a key name made from what the button sends: `bleKeyName(slot, characteristicUuid, bytes)` in `protocol.ts` = "Ble" + slot + short characteristic id + the first six bytes as hex ("Ble1FFE101"), smoke-tested and mirrored by `BleButton.bleKeyName` in the Android agent. **Slots 1–3** (`BLE_BUTTON_SLOTS`, `bleKeySlot`): each device connects up to three buttons, one per slot; buttons of the same make send the same bytes, so the slot is what tells them apart, and a button must sit in the same slot on every device that uses the station. Nothing is assumed about the model: every characteristic that can notify is listened to, a payload is a key going down, and whatever the same characteristic sends next releases it (the same payload again = a new press, for click-only buttons); a payload of only zero bytes is just the release (`bleIsRelease`, smoke-tested; seen on a real "PTT-Z": FFE1 sends 01 down, 00 up → key `Ble1FFE101`). A press of a connected Bluetooth button nobody knows yet fills the first row that has no key (a button added in Admin as "Accept item" without pressing it): in the Buttons panel, and on every other client screen too (`useStationButtons` `onLearn` → `saveButtons`, then the press runs its action; not in Admin, not while a panel is open — `buttonPanelOpen`). The panel also shows presses live (Admin and Home → Buttons): a dot and "Pressed now / Last pressed: <key> → button N, <action>" (or "not set to anything yet"), and the row of the pressed button turns green while it is held (at least 350 ms). The agent logs every payload under the logcat tag `FlowVoiceBle`. Browser: `web/src/ble.ts` (Web Bluetooth, Chrome / Edge only; the chooser needs a click on every page load, then it reconnects by itself; the page may only open the services listed in `SERVICES` — FFE0, FFF0, Nordic UART, Microchip … — plus `?bleservice=<uuid>`, remembered in `fv.bleService`). Android: `BleButton.kt`, one instance per slot (picked once in the system chooser via `CompanionDeviceManager`, so no location permission and no scan of our own; remembered in prefs `bleButton<slot>`, reconnected with `connectGatt(autoConnect)` when the button wakes up; needs "Nearby devices" on Android 12+), bridge `connectButtonSlot(slot, all)` / `buttonState()` (JSON array), long-press menu "Bluetooth buttons…" (slot → find / show all / stop using), state pushed as `window.flowVoiceButtonState(json)`. **The chooser list is short by default** on both: only devices on a button service or with a push-to-talk / remote kind of name (`NAME_STARTS` + `buttonFilters` in `ble.ts`, `BUTTON_NAMES` + `BUTTON_SERVICES` in `BleButton.kt`); "Show all devices" lists everything in reach. `BleButtonLink` ("Connect button N" / "Button N: name ✓") shows all three in Admin → Stations → Buttons (to learn the key by a press) and, for the slots a station's `Ble…` keys use, on Home (`VoiceBar`) and the run screen. Not covered: Bluetooth Classic (SPP) push-to-talk buttons, and Firefox / Safari (no Web Bluetooth). Tested on the SM-T500 tablet with a "PTT-Z" button; the browser path is not tested against real hardware yet.
- **Only the marked words count** (per checklist, Checklist setup → "Accept a plain yes, confirm or no", off = strict): `settings.wordsOnly` (template ids, `PUT /api/library/entry {wordsOnly}`) → `InterpretContext.answersOnly`. An item that has answer words then refuses everything that does not contain one ("hivt körbro" passes, "ja" / "no" get `m_say_word`); items without words, the read-back confirmation and commands (skip, repeat …) are unchanged.
- **Word tolerance** (per checklist, Checklist setup → "How exact must the word be heard"): `settings.wordMatch[templateId]` = `exact` / `normal` (default) / `loose` → `InterpretContext.answerMatch` (`ANSWER_MATCH` 1 / 0.75 / 0.6). `heardAnswer` takes the marked word anywhere in a sentence, inflected or compounded ("körbron", "hovedkörbro"), and near misses by folded-letter edit similarity over 1–3 word windows ("kjørebro", "kjøre bro"); words under 4 letters stay exact, a negation never counts.
- **Commands the hub asked for are taken loosely** (`controlWord(text, true)`: a held item waiting for "next", the menu, a pending or paused run): filler around the word ("ok neste", "neste takk"), a repeat ("neste neste") and a near miss by folded-letter edit similarity ("Nesta", "næste punktet") all count, as do "klar" / "ready" and a "next" word anywhere in a short utterance; volume / speed / "where" stay exact and an item being answered is always exact ("høyre" is an answer, never "høyere"). Every transcript heard in the wait window is audited as `command.heard` with the command it became.
- **Spoken text is cleaned** in `Gateway.speak` (`spokenText` in `i18n.ts`): "/", brackets, underscores, list marks and "&" are never read out; separators between digits stay.
- **Acronym answers** ("vts", "vhf": 2–5 letters, no vowel) also match the spoken letters as a recogniser writes them ("vet tes", "ved TS") by consonant skeleton (`nearAnswer`). Answer words are read live from settings at interpret time (`interpretCtx`), so edits apply to an open run.
- **Less talk**: an answer given with a marked word (`Interpretation.byWord`) never gets the read-back question (`confirmationFor` → none; a binding with `confirmation: "required"` still wins), whatever the control type. The echo after an answer is only the value (`echo_short`) for word answers and for item names over 30 characters. A missed answer gets only the short hint; the full question is repeated on the last try.
- **How much the voice says** (Admin → Stations, on the card): `Station.verbosity` `full` (item number, question, item + value echo) / `short` (question, value-only echo, no counts) / `silent` = "Least" (question only: no start line, section names or echo). `RunEngine.level(r)` reads it live from the station, so a change applies to an open run; prompt runs keep their own.
- **When to read the next item** (per checklist, Checklist setup): `settings.stepMode[templateId]` = `{mode: auto}` (default) / `ask` / `{mode: timer, delaySec}` / `external` (`PUT /api/library/entry {step}`, `LibraryView.step`). `RunEngine.advance` → `hold()`: `exchange: "waiting"`, `RunRecord.waiting {taskId, mode, until}` (also on `RunView`), spoken `step_ask` / `step_timer_sec|min` / `step_external`; released by `proceed(runId, by)`: spoken next / continue / start / confirm, the timer (`armStep`, re-armed on restart and endpoint reconnect, fires at once when overdue), the Run screen's "Next item" (`POST /api/runs/:id/proceed`), or an integration (`POST /v1/runs/:id/proceed`, `POST /v1/stations/:id/proceed`; `/v1/runs/:id/next` also releases). Body `{item}` (DataId or task id, also `dataId` / `taskId`) reads that item at once instead, held or not (`jumpTo`, which drops the hold). In `ask` mode the mic stays open while held (`openWaitListen`, promptId `<runId>:waiting`: control words + the held item's words, re-armed on silence and after anything but "next"); timer / external holds keep it closed. **Quiet hold per station** (Admin → Stations, tick "Say “say next when you are ready” while waiting", `Station.askNext`, default on, read live by `RunEngine.askNext`): off = an `ask` hold says nothing (also on "repeat"), the mic is still open and "next" still releases. Held runs survive endpoint loss and restarts; pause drops the hold. Events `run.waiting` / `run.proceeded`. Prompt runs never hold. `npm run mock` step "step mode".
- **Live sync with the Flow app** (someone ticks an item on a phone while the voice runs): the Checklist API has no subscription, so `voice/FlowWatcher.ts` ticks every open run — a stats-only read (`GET /flows/{id}/values?pageSize=0`, a few hundred bytes) every `SYNC_POLL_MS` (`PolicyEnv.syncPollMs`, default 3000, 0 = push only), the rows (`fields=taskId,dataId,status,value,displayValue,time,type`, `FlowsClient.queryValues`) only once the counts move, plus one forced row read every 10th tick (an edited value leaves the counts equal). The diff is pure (`voice/livesync.ts` `diffExternal` → `answered` / `changed` / `reopened`, `structureChanged` = a task the run does not know → full `refreshItems`); `RunEngine.applyExternal` takes the items over, **never writes anything back** (the value came from Flow), emits `run.item.external` + audit `item.external`, and speaks one short line (`item_elsewhere` / `items_elsewhere` / `item_reopened`, silent stations nothing): the item being asked or held → line, then `advance`; anything else while a mic window is open → screen only. An item in the outbox (`unsynced`) and one the hub is asking again on purpose (`RunItem.reasking`, set by `jumpTo`) are never taken over. Faster than the tick: `POST /v1/flows/:instanceId/changed` (body `{items:[{item, value?, cleared?}]}` applies at once, then one confirming read) and `POST /v1/runs/:id/sync`; `resume`, `onEndpointReady` and a rejected write also sync. Prompt runs (`prun_`) are never watched — they exist to ask one question. A spoken answer over a value Flow already holds wins and says so (`item_override`, "That was High. Setting Alarm."). `npm run mock` step "live sync".
- **Missed item from outside** (a run never moves on by silence, so an item nobody answers holds it, e.g. a reporting point the vessel already passed): `POST /v1/runs/:id/missed` / `POST /v1/stations/:id/missed`, body `{item?, value?}` (`item` = DataId or task id, also `dataId` / `taskId`; none = the item asked or held now). `RunEngine.missed`: speaks `item_missed`, then with `value` ("No", an option title or value, any case) writes it as the signed-in user (`answerManual`, 409 `NO_USER` without one), without `value` (or "no" on a plain checkbox) the item is skipped with reason `missed` and comes back in the sweep. The run goes on; a held item hands the hold to the one after it; an item already answered is left alone. Event `run.item.missed`, audit `item.missed`. `npm run mock` step "step mode".
- **Sign-out leads back to the Maranics sign-in**: `POST /api/auth/logout` sets the `fv_fresh` cookie (1 h, `/api/auth`); the next `GET /api/auth/login` consumes it and sends `prompt=login` (`AuthorizeParams.prompt`, beats `HUB_OIDC_PROMPT`), so a Maranics session that is still alive does not drop the person straight back in: they can sign in as someone else or pick another location. Sign-out also clears the tokens: the session row with its sealed tokens is deleted and refresh + access token are revoked at Maranics (`OidcClient.revoke`, RFC 7009 `revocation_endpoint` from discovery, best effort; `Credentials.tokensOf`). With `HUB_OIDC_POST_LOGOUT_REDIRECT_URI` set the Maranics session is ended as well. `npm run mock` step "tenants".
- **Recogniser alternatives**: browsers ask for five guesses (`maxAlternatives`) and send the rest as `transcript.alternatives`; `RunEngine.onTranscript` swaps in the first guess that holds one of the item's answer words when the top guess holds none (`bestTranscript`, pure, smoke-tested). Chrome / Edge Norwegian is weak on ship terms; this plus word tolerance is the remedy, not server Whisper (tested: no better, and a comma-list prompt makes it hallucinate "Ja, bekreft").
- **Takeover never ping-pongs**: a client closed with 4409 (replaced) stops (`onReplaced`) and tells the user; it reconnects only on Start voice. Never open a second `/client` tab on a station with `audioPolicy: "open"` while testing: it takes the voice away from the crew.
- **Day / Night switch**: the client header (every screen, sticky) has one large two-state button (`useDayNight` in `web/src/theme.ts`, no "auto" step) for light-sensitive places; it pins `fv.theme` and tells the Android agent via `setTheme`. The desktop admin keeps the three-state cycle.
- **Start buttons**: `settings.startable` (template ids, Admin → Start buttons, `PUT /api/settings`) limits what the phone / tablet home and the voice menu offer; empty → all. `ChecklistPick.startable` carries it; every client view honours it.
- **Phones / tablets have no settings.** Station comes only from a QR poster (`Home.tsx` shows a scan screen until `me.stationSource === "join"`; "Change station" calls the Android bridge `scanStation()`; the agent turns a poster link into hub origin + `#/join/<token>` and forces a full load). Language, answer language and hold-to-answer controls are desktop-only: on mobile the hello language is the station's, `Station.holdToAnswer` drives hold mode, and the run language rides in `listen.open.language`. Admin → Stations has a one-step "Create + QR" form.
- **Browser TTS voice**: `pickVoice(tag)` in `web/src/audio.ts` sets `utterance.voice` explicitly (exact tag, then same language; Norwegian = nb / no / nn), after waiting for Chrome's late voice list. A `lang` tag alone leaves Chrome / Safari on the default English voice. No matching voice → one `onError` hint telling where to install it.
- **Language order for a run**: checklist language (station rule, then Checklist setup) > language the client reported in `hello` > profile > station > default. `onEndpointReady` and resume re-apply it, so a client that connects later (it reports the station language) never resets a checklist to English.
- **Checklist language per template**: `settings.templateLanguages` (Admin → Start buttons) wins over endpoint / profile / station language in `RunEngine.newRun` and `trigger`.
- **Checklists per station**: `Station.templates[templateId] = { access?: "start" | "use" | "off", language? }` (Admin → Stations → "Checklists on this station", portable in `stations.json`). `start` = start button + work on open ones, `use` = only open ones started elsewhere, `off` = hidden. The admin adds templates to the station (add-list with language); a station with entries offers only those, a station with none → the hub-wide Start buttons list. Station cards in Admin are an accordion (collapsed by default). `RunEngine.templateAccess` / `templateLang(id, station)` decide; `ChecklistPick.access` + `startable` carry it (instances: startable = not `off`), the voice menu follows, and `start()` refuses with 403 `NOT_STARTABLE_HERE` / `NOT_USED_HERE`. Triggered runs are not filtered. The station language per template beats `settings.templateLanguages`.
- **Speech models from the hub**: `server/speech/models.ts` serves `GET /models/vosk/<lang>.zip` (public) from `<data>/models/vosk/`, fetching upstream once if missing; `POST /api/models/vosk/:lang` (admin) prefetches. `VoskStt` tries the hub, then the public mirror. No Vosk model exists for Norwegian: it uses the system recogniser, and on Android 13+ the agent calls `triggerModelDownload` for a missing offline pack.
- **Speech recognised on the hub per station** (Admin → Stations, "Where speech is recognised (computers)", `Station.speech` `device` (default) / `hub`, portable in `stations.json`, select disabled without `boot.speech.sttBackup`): `voice.tsx` passes `hubStt` and `audio.ts` then reports `localStt: false` and streams PCM, so `Gateway.closeCapture` transcribes with the backup adapter; same as `?hubstt=1` but set once by the admin. Streamed windows have a **silence detector** in the browser (`onPcm` in `audio.ts`: RMS per 20 ms chunk, noise floor that follows quiet fast and loud slowly, speech = 80 ms above 3× floor, window ends 800 ms after speech stops) so the hub recogniser answers as fast as the browser's; a window with no speech at all ends with `audio.end {reason: "empty"}` and the Gateway treats it as silence without running the recogniser. `speakFromHub` aborts the TTS fetch after 6 s (browser voice takes over). Phones ignore the setting. Compose profile `speech` (`deploy/docker-compose.yml`: `stt` = whisper.cpp with `./models/ggml-small-q5_1.bin`, `tts` = Piper) + `STT_BACKUP_ENDPOINT` / `TTS_ENDPOINT` in `.env` turn it on.
- **Backup recognition on the hub** (`STT_BACKUP_ENDPOINT`, OpenAI-compatible; `deploy/whisper/Dockerfile` = whisper.cpp server, `-ac 384`, quantised model, idle = 0 CPU). Devices still transcribe themselves. Android (`VoskStt`): the voiced part of a window (≤ 7.5 s, RAM only) is POSTed to `POST /api/stt` (session cookie from the WebView, one job at a time, ≤ 8 s, no-speech filter in `HttpStt`) only when the grammar recogniser heard speech but matched nothing; languages without a Vosk model (Norwegian) use `startListeningServer` (energy endpointer, no recogniser on the phone) for prompt windows, never for the idle window. Browsers without a usable `SpeechRecognition` (Raspberry Pi Chromium, offline Chrome → `fv.hubStt`, `?hubstt=1|0`) stream PCM and the Gateway transcribes with the backup adapter. `boot.speech.sttBackup` tells clients it exists.
- **One link per station, no station control in any client**: every station always has a join token (`ensureJoins`, minted on station save / admin read); it is kept sealed with the hub key (`StationJoin.sealed`) so admins get `StationView.join.path` (`/client#/join/<token>`) and the QR again at any time. "New link" rotates it (old one dies); revoke = rotate. Home shows "open the station link" until `stationSource === "join"` on every device; spoken "station …" answers `station_fixed`. **The device keeps its station across sign-out**: a link / code that joined is remembered in the device's `localStorage` (`fv.stationJoin`, `savedJoin` / `rememberJoin` in `App.tsx`; the Android WebView keeps it too), and boot (`probe(true)`) redeems it again whenever the session is not bound by a link, so signing out and in never means scanning the poster again. A rotated link or code (`JOIN_INVALID` / `BAD_REQUEST`) is forgotten; offline / rate limited is retried next boot.
- **Direct links**: `/client` = run-and-voice client on any device (wins over UA detection and `fv.mobile`), `/admin` = desktop admin; `/` keeps detecting. Station posters point at `/client#/join/<token>` (old `/?mobile=1#/join/…` posters still work); sign-in carries `returnTo` so the path survives OIDC.
- **Clients**: one PWA for Android (agent APK), macOS, Windows and Raspberry Pi (Chromium kiosk). TTS is the browser's `speechSynthesis` (a Pi needs `speech-dispatcher` + `espeak-ng`, or `TTS_ENDPOINT`).
- **Discard and Complete are screen-only**; spoken "discard" only reminds the user.
- **Complete asks twice on screen**: when the last item is done the hub says "All items done. Complete the checklist? Press Complete." (`complete_it`); the Run screen button calls `POST /api/runs/:id/complete-tap` → `RunEngine.completeTap`: first press arms it for 15 s (`RunRecord.completeArmedUntil`, on `RunView`; button reads "Press again to confirm") and says `complete_tap_again` (not awaited, so a second press is never dropped as "in flight"), the second completes. A hardware `accept` once every item is answered does the same (`RunEngine.button` → `completeTap`) and says `completed`. `/complete` (and `/v1/runs/:id/complete`) still complete in one call. **Starting a checklist from Home goes straight into open mode**: voice starts and hands-free is switched on. One checklist at a time per station stays (409 `RUN_ACTIVE`). `npm run mock` covers the two presses.
- **Server-side voice** (`TTS_ENDPOINT` = Piper HTTP server, `deploy/piper/Dockerfile`, voices baked in; `TTS_VOICES` overrides the language → voice map in `server/speech/tts.ts`): `GET /api/tts?lang=&text=` (session, ≤ 600 chars, RAM cache, nothing on disk) returns a WAV. Browser clients (`serverTts`, `speakFromHub` in `audio.ts`) play it instead of `speechSynthesis`, so every computer uses the same voice in the checklist language; any failure (no voice for the language, hub down, autoplay refused) falls back to the browser voice. The Android agent keeps its own TTS engine.
- **Central admin area** `/central` (`web/src/pages/Central.tsx`, rendered by `main.tsx` before `App`): its own password `CENTRAL_PASSWORD` (≥ 12 chars), `POST /api/central/login` (rate limited, timing-safe) → signed `fv_central` cookie (12 h), `GET /api/central/me`, `POST /api/central/logout`; all in `server/tenants.ts`. With the password set, only a central session adds / opens / removes tenants (`/api/tenants*`); without it, main-hub admins do (dev). `npm run mock` runs with it set.
- Everything runs on Windows, macOS and Linux via Node launchers (`scripts/*.mjs`); no shell built-ins in npm scripts.
